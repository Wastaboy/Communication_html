What Part 5 builds

TL;DRTwo Power Automate flows — CBF - New Request Notification (email the CCD team on every submission) and CBF - Audit Logger (a reportable row in Audit Log for every create, edit and status change) — plus an optional requester notification, test-data cleanup, and the full ten-point acceptance walkthrough that takes the system live.

Before you start

Prerequisites

  • Parts 1–4 finished and published.
  • Access to make.powerautomate.com in the same environment as the app.
  • A colleague (or IT test account) for the two-person go-live walkthrough in e10.

The steps

E1Notification flow — the trigger
  1. Go to make.powerautomate.com; confirm the environment picker (top-right) shows the same environment as the app.
  2. + Create → Automated cloud flow. Flow name: CBF - New Request Notification.
  3. In the trigger search type When an item is created and pick SharePoint · When an item is created → Create.
  4. Site Address: pick your site. List Name: Communication Requests.
Lookalike triggersThree near-misses sit next to the right one: When an item is created or modified (that's e4's trigger, not this one), When a file is created (properties only), and Dataverse's When a row is added. Pick the plain SharePoint When an item is created.
Check before moving onThe trigger card shows your site and Communication Requests.
E2Notification flow — the email
  1. + New step → search Send an email (V2) → pick Office 365 Outlook · Send an email (V2).
  2. To: Corporate.Communications@bbkonline.com
  3. Subject: type New Communication Briefing Request: then add dynamic content Request Subject (open the lightning-bolt panel if it's collapsed).
  4. Body — paste this, then replace each [bracket] with the matching dynamic content chip:

email body · paste, then swap [brackets] for dynamic content

A new communication briefing request has been submitted. Subject: [Request Subject] Department: [Department Value] Target date: [Target Date] Details: [Request Details] Open the request: [Link to item]
  1. Save.
Confirm with CCDShared mailbox vs individuals: the spec allows either Corporate.Communications@bbkonline.com or the five members directly. For individuals, put all five addresses in To separated by ;.
First-run sign-inThe Outlook connector asks you to sign in the first time — your BBK account, as usual.
Check before moving onFlow checker (top-right) shows no errors and the flow is saved.
E3Test the notification
  1. Open the published app (or F5 in studio) and submit a fresh request: TEST notify - delete me later.
  2. Within about a minute, the CCD address receives the email; the item link opens the request.
  3. In Power Automate, the flow's run history shows Succeeded.
Emails come from youThe flow sends through your Outlook connection — recipients see your name as sender. That's fine for Phase 1; a service-account sender is an IT enhancement for later.
Check before moving onEmail received, link works, run history green.
E4Audit flow — the trigger
  1. + Create → Automated cloud flow → name CBF - Audit Logger.
  2. Trigger: SharePoint · When an item is created or modified — this time you want the "or modified" one (mirror image of the e1 warning).
  3. Site Address: your site. List Name: Communication Requests.
Check before moving onTrigger card configured for Communication Requests.
E5Audit flow — created or edited?
  1. + New step → Condition.
  2. Left value: dynamic content Created. Operator: is equal to. Right value: dynamic content Modified.
  3. In the If yes branch: Add an action → SharePoint Create item → Site, List Name Audit Log, and map:
Audit Log fieldValue
Titledynamic Request Subject
RequestIDdynamic ID
Action ValueCreated
ModifiedBydynamic Modified By DisplayName
ModifiedDateTimedynamic Modified
ChangeSummaryNew request submitted
Why Created = Modified means "new"SharePoint stamps both timestamps identically at creation; any later edit moves Modified. One comparison sorts every run into created vs edited — no extra queries.
Check before moving onThe yes-branch Create item card is fully mapped.
E6Audit flow — was it a status change?

All of this goes in the If no branch (the item was edited — but was it the Status column?).

  1. Add an action → SharePoint Get changes for an item or a file (properties only): Site, List = Communication Requests, Id = dynamic ID. For Since, open Expression and paste:

Get changes · Since (expression)

triggerOutputs()?['body/{TriggerWindowStartToken}']

Get changes · Until (expression)

triggerOutputs()?['body/{TriggerWindowEndToken}']
  1. Then a nested Condition: left = dynamic Has Column Changed: Status, is equal to, right = expression true.
  2. Nested yes: Create item in Audit Log — same six mappings as e5 except Action Value = Status Changed and ChangeSummary = this expression:

ChangeSummary (expression, nested yes)

concat('Status is now: ', triggerOutputs()?['body/Status/Value'])
  1. Nested no: Create item in Audit Log — Action Value = Edited, ChangeSummary = Fields updated by requester or CCD, same other mappings.
  2. Save.
Why "Get changes"The trigger alone can't see which column moved. Get changes compares the item against the trigger window and hands you per-column changed flags — the honest way to label a row "Status Changed".
Check before moving onThree Create item actions exist in total (e5 yes; e6 nested yes and no); flow checker is clean.
E7Test the audit trail
  1. Submit a new request from the app: TEST audit - delete me later.
  2. Edit it from My Requests (change the details).
  3. Change its status from the CCD dashboard.
  4. Open the Audit Log list: three new rows — Created, Edited, Status Changed — each with the editor's name and timestamp.
FR-4, met and reportableEvery edit now has who + when in a flat list that exports to Excel — the audit requirement in full, alongside version history.
Check before moving onAll three action types present with correct names and times (runs can take a minute — refresh the list).
E8Optional — status-change email to the requester
Optional stepThe spec left this open (should requesters get an email when CCD updates their status?). Confirm with CCD — skip this step entirely and mark it done if they say no; My Requests already shows status live either way.
  1. New automated flow: CBF - Status Change Notification, trigger When an item is created or modified on Communication Requests.
  2. Get changes for an item or a file (properties only) — same Since/Until expressions as e6.
  3. Condition with two rows (AND): Has Column Changed: Status is equal to expression true, and dynamic Created is not equal to dynamic Modified.
  4. If yes → Send an email (V2): To = dynamic Created By Email; Subject = Your communication request status: + dynamic Status Value; Body = a short line plus dynamic CCD Notes and Link to item. Save.
Why the second condition rowWithout Created ≠ Modified, brand-new items (whose Status "changed" from nothing to Submitted) would email the requester about their own submission.
Check before moving onEither the flow is built and a dashboard status change emails the requester — or CCD said no and you skipped it. Both count.
E9Go-live — clean the test data
  1. In Communication Requests, filter or search for TEST and delete every seeded item (a9, b9, e3, e7 and any strays).
  2. Delete the matching Audit Log rows the tests created.
Recycle bin ≠ hard deleteDeleted items sit in the site recycle bin for 93 days — consistent with the "no hard-delete" spirit of FR-8; real requests are never deleted at all, only archived by status.
Check before moving onBoth lists contain zero TEST rows.
